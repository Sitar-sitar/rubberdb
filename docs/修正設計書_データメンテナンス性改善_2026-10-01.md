## 1. 目的・背景

データは `client/src/lib/rubberData.ts` の 1 ファイル（73 KB、159 製品・11 ブランド）にあり、2026-08-17 以降 6 回の追加が行われている。現状の追加作業には次の問題がある。

| # | 問題 | 実測 |
|---|---|---|
| 1 | 1 製品が 1 行に詰まっていて、差分が読めない | 1 行 400〜515 文字。16 項目が横並び |
| 2 | `priceLabel` を `price` と二重に手入力している | 159 件すべてが `price` から機械的に導出できる（数値は「N,NNN円（税込）」、`null` は「オープン価格」）。整合はテストで後追い検査している |
| 3 | ブランドを追加すると 4 ファイル 4 箇所を直す必要がある | `Rubber["brand"]` の union（`rubberData.ts`）、`brandTint`（`utils/brandTint.ts`）、`sources`（`rubberData.ts`）、許可ホスト（`tests/unit/rubberData.test.ts`） |
| 4 | 追加が診断結果へ与える影響が、追加時に見えない | 診断は 54 通りの条件があり、同点はデータの記載順で決まる。現在のテストは結果そのものを固定していない |
| 5 | 公開済み ID の変更・削除を止める仕組みがない | v1.1.1 から、カタログに無い ID のお気に入りは読み込み時に削除される。ID を変えると利用者の保存データが黙って消える |
| 6 | 追加手順がどこにも書かれていない | `README.md` は 14 行で、デプロイ構成のみ |
| 7 | 過去の調査メモがリポジトリ直下に散らばっている | 直下に `*-spec.md` / `*-research.md` など 18 ファイル |
| 8 | 使われていないデータ API が残っている | `playStyles`、`getRecommendedRubbers`（画面から未使用） |

バンドルサイズにも余裕が少ない。JS は 372.3 kB で、成果物検査の上限 400 kB まで約 28 kB。1 製品あたり約 0.4 kB なので、このままだと 70 製品ほどの追加で CI が落ちる。

## 3. 全体方針

- **先に網を張ってから動かす。** 最初に M-04 のスナップショットを現行コードで作成し、以降の各 Step でスナップショットが変わらないことを確認する。これが「挙動を変えていない」ことの根拠になる。
- **カタログの並び順を変えない。** 並び順はカタログの表示順と、診断の同点時の勝敗を決めている。現行データは 159 件すべてがブランドごとに連続して並んでいる（Butterfly 19 → Nittaku 19 → VICTAS 20 → Yasaka 22 → TIBHAR 15 → XIOM 15 → STIGA 20 → DONIC 16 → andro 3 → JOOLA 8 → JUIC 2）ため、ブランド別に分割して同じ順で連結すれば順序は完全に保たれる。
- **導出できるものは持たない。** `priceLabel`、ブランドの union 型、バッジ色の表、公式ソース一覧、許可ホストは、いずれも 1 つの定義から導出する。
- **既存の import を壊さない。** `@/lib/rubberData` は入口として残し、`rubbers` / `sources` / `chinaGuideRubberIds` と型を従来どおり export する。画面側の変更は `priceLabel` の 6 箇所と `brandTint` の参照だけに留める。
- **ディレクトリは共通ルールの 4 種（`components` / `lib` / `utils` / `types`）に収める。** 新しい最上位ディレクトリは作らない。

## 4. 詳細仕様

### M-01 ブランド定義の一元化

`client/src/lib/brands.ts` を新設し、ブランドに関する情報をここだけに書く。

```ts
export const brands = [
  {
    id: "Butterfly",
    tint: "bg-[#fff0ec] text-[#a53d30]",
    sourceName: "Butterfly ラバー製品情報",
    sourceUrl: "https://www.butterfly.co.jp/products/rubber/",
    hosts: ["www.butterfly.co.jp"],
  },
  // …11 ブランド。配列の順序がカタログとフッターの表示順になる
] as const;

export type BrandId = (typeof brands)[number]["id"];
```

- 同ファイルから導出して export するもの：
  - `brandTint: Record<BrandId, string>`（現 `utils/brandTint.ts` と同じ値）
  - `sources: { name: string; url: string }[]`（現 `rubberData.ts` の `sources` と同じ内容・同じ順）
  - `allowedSourceHosts: ReadonlySet<string>`（現テスト内の `ALLOWED_SOURCE_HOSTS` と同じ集合）
- `Rubber["brand"]` の型は `BrandId` にする。
- `client/src/utils/brandTint.ts` は削除し、`Home.tsx` の import 先を `@/lib/brands` に変える。
- `tests/unit/rubberData.test.ts` の `ALLOWED_SOURCE_HOSTS` は削除し、`allowedSourceHosts` を使う。
- andro は現状、製品の出典が `andro.jp`、ソース一覧が `www.andro.de` で食い違っている。今回は現状の値をそのまま移し、`hosts` に両方を入れる（§10-3）。

**ブランド追加時の編集箇所：4 ファイル 4 箇所 → `brands.ts` の 1 要素とブランド別データファイル 1 つ（M-03）。**

### M-02 `priceLabel` の廃止

- `Rubber` 型から `priceLabel` を削除する。
- `client/src/utils/price.ts` に `formatPriceLabel(price: number | null): string` を追加する。
  - 数値：`` `${price.toLocaleString("ja-JP")}円（税込）` ``
  - `null`：`"オープン価格"`
- `Home.tsx` の `rubber.priceLabel`（6 箇所）を `formatPriceLabel(rubber.price)` に置き換える。
- `rubberData.test.ts` の「priceLabel と price が矛盾しない」は対象が無くなるため削除する。
- 移行の安全確認として、**削除前に** 「全 159 件で `formatPriceLabel(price) === priceLabel`」を 1 回実行して一致を確認し、結果を実装ログに残す（このテスト自体はコミットしない）。

### M-03 型の分離とブランド別ファイル分割

```
client/src/types/rubber.ts          Rubber / RubberType / PlayStyle / Hardness（型のみ）
client/src/lib/brands.ts            M-01
client/src/lib/rubbers/butterfly.ts ブランドごとに 1 ファイル（11 ファイル）
client/src/lib/rubbers/nittaku.ts
  …
client/src/lib/rubberData.ts        入口。連結と再 export のみ
```

- ブランド別ファイルは、`brand` を除いた製品の配列を `export default` する。型は `RubberEntry = Omit<Rubber, "brand">`。

```ts
// client/src/lib/rubbers/juic.ts
import type { RubberEntry } from "@/types/rubber";

const rubbers: RubberEntry[] = [
  {
    id: "juic-999-elite",
    name: "JUIC999エリート",
    type: "裏ソフト",
    price: 4290,
    hardness: "中",
    country: "日本",
    speed: 3,
    spin: 5,
    control: 4,
    styles: ["sticky", "spin", "control"],
    suitableFor: "粘着系の高回転と軽量性を両立したい人",
    source: "https://www.juic.co.jp/view/item/000000000083",
    officialNote: "日本製粘着ゴムシート＋日本製スポンジ／硬度M",
    verifiedAt: "2026-08-25",
  },
];

export default rubbers;
```

- `rubberData.ts` はブランドごとに `brand` を付けて連結する。連結順は `brands.ts` の配列順と同じ（＝現行の並び順）。

```ts
const withBrand = (brand: BrandId, entries: RubberEntry[]): Rubber[] =>
  entries.map(entry => ({ ...entry, brand }));

export const rubbers: Rubber[] = [
  ...withBrand("Butterfly", butterfly),
  ...withBrand("Nittaku", nittaku),
  // …
];
```

- ブランド別ファイルと `brands.ts` には Prettier を掛け、1 項目 1 行にする。
- `rubberData.ts` からは `rubbers` / `chinaGuideRubberIds` / `sources`（`brands.ts` からの再 export）と型（`types/rubber.ts` からの再 export）を出す。`Home.tsx` とテストの import 文は変えなくてよい。
- ファイル名はブランド ID の小文字（`butterfly` / `nittaku` / `victas` / `yasaka` / `tibhar` / `xiom` / `stiga` / `donic` / `andro` / `joola` / `juic`）。

### M-04 診断結果のスナップショットテスト

- `tests/unit/recommend.snapshot.test.ts` を新設する。
- 経験 2 × 予算 3 × フォア 3 × バック 3 ＝ 54 通りについて、`suggestSet` の結果から「フォア ID、バック ID、フォア候補の上位 4 件の ID、バック候補の上位 4 件の ID」を 1 行の文字列にし、Vitest のファイルスナップショット（`toMatchSnapshot`）で固定する。上位 4 件は、画面の「ほかの候補も比べる」に出る範囲と一致する。
- **運用**：製品を追加して診断結果が変わるとテストが落ちる。変化が意図どおりなら `pnpm test -u` で更新し、スナップショットの差分をコミットに含める。差分がそのまま「この追加で提案がどう変わったか」のレビュー対象になる。

### M-05 データ検査の追加

`tests/unit/rubberData.test.ts` に追加する。いずれも現行データで pass することを確認済みの項目に限る。

| 検査 | 目的 |
|---|---|
| `id` が `^[a-z0-9-]+$` | ID の表記ゆれ防止（お気に入りのキーになるため） |
| ブランド＋製品名の重複なし | 同じ製品の二重登録を検出 |
| `name` / `suitableFor` / `officialNote` が空でない | 入力漏れの検出 |
| `verifiedAt` が実行日の翌日以前 | 未来日の入力ミスを検出（タイムゾーン差の 1 日は許容） |
| `source` のホストが、その製品のブランドの `hosts` に含まれる | 別ブランドの URL の貼り間違いを検出（現行は全ブランド共通の許可リストで検査） |
| `brands.ts` の全ブランドに製品が 1 件以上ある | 定義だけ残ったブランドを検出（現「brandTint に未使用のブランドが残っていない」を置き換え） |

`country` の必須化は入れない（§10-1）。

### M-06 公開済み ID の台帳

- `tests/unit/publishedIds.json` を新設し、公開済みの ID を配列で持つ（初期値は現行 159 件）。
- テストを 2 つ追加する。
  1. **台帳にある ID はすべてカタログに存在する。** ID の変更・削除で落ちる。メッセージに「公開済み ID は変更・削除できない。利用者のお気に入りが消える」と出す。
  2. **カタログの ID はすべて台帳にある。** 追加時に台帳への追記を強制する。
- 台帳から ID を消すのは、廃番を意図して決めたときだけ。その手順は README に書く（M-07）。

## 7. リスクと割り切り

- **分割時の書き写しミス**が最大のリスク。Step 2 の基準 JSON と Step 5 後の `rubbers` を、件数・順序・全項目で機械比較して防ぐ。
- **スナップショットは「変化の検出」であって「正しさの保証」ではない。** 現在の偏った提案（54 通りで 13 製品）をそのまま固定する。採点式を見直すときは、スナップショットの更新を前提にする。
- **`verifiedAt` の未来日検査は実行日に依存する。** 1 日の余裕を持たせ、時刻起因の誤検出を避ける。
- **ID 台帳は追加のたびに 1 行の手間が増える。** 代わりに、ID の変更・削除という利用者データを壊す操作を必ず検出できる。
- **メモの移動で、過去のコミットメッセージや外部からの直下パス参照は切れる。** リポジトリ内からこれらのメモへのリンクは無いことを実装時に `grep` で確認する。
- **ロールバック**：各 Step が独立したコミットなので、該当コミットの revert で戻せる。利用者データの移行は無い。

## 8. テスト・検証

- **基準との一致**（Step 5）：分割前後の `rubbers` を JSON 化して比較し、差分 0 を確認する。
- **価格表記の一致**（Step 3）：全 159 件で `formatPriceLabel(price) === priceLabel`。
- **スナップショット**：Step 1 で作成後、Step 3〜8 のすべてで更新なしに pass する。
- **追加した検査の否定テスト**（手元で確認し、結果を実装ログに残す）：
  - 既存 ID を 1 件書き換える → M-06 のテストが落ちる。
  - 製品を 1 件追加して台帳に書かない → M-06 のテストが落ちる。
